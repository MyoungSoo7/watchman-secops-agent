# 호스트 경보 E2E 카나리 — 결함 3건과 수정 (2026-09-25)

`real-alerts-20260924.md` §2.1 에서 가장 약한 규칙은 호스트 레벨 `Read sensitive file untrusted`(2/7)였다.
그때는 원인을 "호스트 인증 로그가 ES 에 없다" 로 적었다. 그 뒤 호스트 auth 로그를 수집했다(`log_source:host-auth`).
그런데도 판정 근거에 그 로그가 나오지 않았다. 이 문서는 그 이유를 카나리로 끝까지 따라간 기록이다.

## 카나리 방법

- david 노드에서 읽기 전용 sudo 명령을 한 번 실행한다(예: `sudo -n wc -l /etc/pam.d/common-session`).
  파일을 바꾸지 않는다. 사용자 승인 뒤에 실행했다.
- 기대 경로: Falco `Read sensitive file untrusted`(warning) → falcosidekick → Alertmanager → Watchman 웹훅
  → `es_search` 가 host-auth 의 sudo 기록을 찾는다 → 카드 근거에 `COMMAND=...` 줄이 들어간다.
- 판정은 감사로그(`/data/audit.jsonl`)의 `alert_in`·`tool`·`finish`·`card_sent` 로 확인한다.

## 결함 ① — 경보가 Watchman 에 닿지 않았다 (Alertmanager 억제)

- 기존 억제 규칙: `severity=critical` 이 있으면 `equal: [namespace, alertname]` 이 같은 warning 을 억제한다.
- Falco 경보에는 `namespace`·`alertname` 라벨이 없다. Alertmanager 의 `equal` 은 **라벨이 없는 것끼리도 같다고 본다.**
  그래서 어느 노드에서든 Falco critical(CI 의 `Drop and execute`) 1건이 뜨면, 클러스터 전체의 Falco warning 이 묻혔다.
- 실측(9/24~25, ES 의 Falco 원본과 Watchman 수신을 대조): critical 이 ±5분 안에 있을 때는 warning **192건 중 146건**을
  받지 못했다. 없을 때는 **109건 중 4건**이었다.
- 수정: 두 억제 규칙의 source 에 `alertname != ""` 를 더했다(helm-deploy `48244f4`). Prometheus 경보에는 항상
  alertname 이 있으므로 기존 억제는 그대로 동작한다. 적용된 Alertmanager 설정에서 조건 2건을 확인했다.

## 결함 ② — 검색은 됐는데 아무것도 찾지 못했다 (`es_search`)

지난 이틀치 실제 조사(31 run)의 `es_search` 호출 60건을, 당시 시각 창 그대로 ES 에 다시 던져 적중 여부를 셌다.

| 검색 방식 | 적중(>0) 호출 |
|---|---|
| 옛 방식 (`simple_query_string`, 자기 로그 포함) | 33/60 — 대부분 Watchman 자기 로그 |
| 옛 방식, 자기 로그 제외 | **8/60** |
| `query_string` + 자기 로그 제외 (`7dc5b33`) | **19/60** |
| + 경보 라벨 필드 이름을 ES 경로로 치환 (`28f96b7`) | **35/60** (2건은 긴 창의 정규식 조회에서 타임아웃) |

- 모델이 쓴 검색어 60건 중 **51건(85%)** 이 `필드:값` 문법이었다. 옛 방식은 이 문법을 지원하지 않는다.
- 필드 이름도 어긋났다. 모델은 경보 라벨 이름(`container_id`, `proc_cmdline`, `fd_name`)을 그대로 썼다. ES 에는
  `output_fields.container.id` 같은 경로로 저장돼 있다. `query_string` 으로 바꾼 뒤에도 필드 문법 검색 51건 중
  40건이 0건이었던 이유다. 이제 도구가 필드 이름만 치환한다. 큰따옴표 안의 구문 검색은 건드리지 않는다.
- Watchman 자기 로그(자기가 던진 검색어가 찍힌 줄)는 검색 결과에서 뺐다. 전에는 이 로그가 적중으로 잡혀
  근거가 있는 것처럼 보였다.

## 결함 ③ — CI 경보 폭주 뒤에 진짜 경보가 줄을 섰다

- Falco 경보는 `namespace`·`alertname` 이 없어서 Alertmanager 가 전부 **한 그룹, 한 페이로드**로 보낸다.
- Watchman 은 한 페이로드 안의 경보를 한 건씩(약 1분) 차례로 조사한다. CI 가 `Drop and execute` 를 26건 쏟으면,
  그 뒤에 들어온 진짜 경보는 약 26분 뒤에 조사된다.
- 수정(`970ec8b`): 페이로드 안의 경보를 룰별로 묶는다. 건수가 적은 룰부터 한 건씩 번갈아 꺼낸다. 혼자 온 경보가
  맨 앞으로 오고, 폭주한 룰도 빠짐없이 조사된다. 순서만 바뀐다(회귀 테스트 3건).
- 한계: 조사 자체는 여전히 한 건씩 한다. NIM 동시 호출 한도(`NIM_CONCURRENCY=2`)가 있어서 병렬로 돌려도
  처리량이 크게 늘지 않는다.

## 한계 — 이 숫자를 어떻게 인용하면 안 되는가

1. 카나리는 **1노드(david)·1종 명령**이다. 통과 1회를 탐지율로 일반화하지 않는다.
2. `real-alerts-20260924.md` 의 `Read sensitive` 2/7 은 **다시 채점하지 않았다.** 그 run 들은 이미 옛 검색으로
   판정이 끝났다. 수정 효과는 위 재검색 표(적중 호출 수)로만 제시한다. 적중이 늘었다고 판정 정답률이 같이
   오른다는 보장은 없다.
3. 재검색은 **지금 ES 에 남은 로그**로 했다. 보존 기간이 지나 사라진 로그는 셀 수 없다.
4. 억제 실측 146/192 는 critical 과 warning 의 시각 근접(±5분)으로 억제 여부를 추정한 값이다. Alertmanager 가
   건별 억제 기록을 남기지 않기 때문이다. 수정 뒤 카나리 4 가 도착한 것은 1건의 직접 확인이다.
