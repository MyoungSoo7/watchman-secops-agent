# 모델 크기별 도구 호출 성공률 (2026-09-24)

**질문:** 파수꾼 에이전트 루프를 더 작은(싼) 모델로 돌려도 도구 호출 규약을 지키는가?
**재는 것:** 분류 정답률이 아니라 *도구 호출 규약 준수*다 — JSON 형식, 인자 검증 통과, 스텝 예산 안 완주.
분류 정답률은 [report-20260922.md](report-20260922.md) 가 다룬다.

재현:

```bash
NIM_MODEL=<모델ID> python3 eval/run_model_size.py 1 out/<모델>.json   # NVIDIA_API_KEY 필요
python3 eval/summarize_model_size.py out/*.json

# 이 문서의 표 = 커밋된 원자료 재집계
python3 eval/summarize_model_size.py eval/model-size-20260924/*.json
```

## 공정성 장치

- **같은 관측:** 클러스터·로그 도구의 네트워크 응답을 고정 스텁으로 바꿨다(`_http_json`·`urlopen` 가로채기).
  모델마다 같은 관측을 받으므로 차이는 모델에서만 나온다. **인자 검증은 실제 코드 그대로**다 — 스텁은
  검증을 통과한 뒤의 네트워크 호출만 대신한다.
- **폴백 끔**(`NIM_FALLBACK_MODELS=""`). 켜 두면 작은 모델의 실패를 큰 모델이 메운다.
- 가드·skill·recovery 게이트 끔. 프롬프트·스텝 예산(6 + 유예 2)·온도(0.2)·타임아웃(120s)은 운영과 같다.
- **NIM 호출 자체 실패**(429·503 재시도 소진, 읽기 타임아웃)는 모델 능력이 아니므로 분모에서 뺐다.
  1차 실행(4모델 병렬)에서 실패한 케이스만 부하를 낮춰 재실행했고, 케이스별로 NIM 이 끝까지 응답한 run 을 쓴다.
- 케이스: `fixtures/cases/` 10 + `fixtures/scenarios/` 4 = 14. 케이스당 1회.

## 결과

| 모델 (ID 표기 파라미터) | 유효 run | 완주 | 도구 1회 이상 | 첫 응답 유효 | 도구 호출 성공 | 인자 거부 | 형식 오류 | 평균 LLM 호출 |
|---|---|---|---|---|---|---|---|---|
| `meta/llama-3.2-11b-vision-instruct` (11B) | 14 | 14/14 | 14/14 | 14/14 | **41/47 (87%)** | 6 | 0 | 4.4 |
| `nvidia/nemotron-3.5-lightning-30b-a3b` (30B, 활성 3B) | 3 | 3/3 | 3/3 | 3/3 | 13/13 † | 0 | 0 | 5.3 |
| `nvidia/nemotron-3-super-120b-a12b` (120B, 활성 12B) — **운영 기본** | 14 | 14/14 | 14/14 | 14/14 | **58/58 (100%)** | 0 | 0 | 5.1 |
| `nvidia/nemotron-3-ultra-550b-a55b` (550B, 활성 55B) | 14 | 14/14 | 14/14 | 14/14 | **63/64 (98%)** | 1 | 1 | 5.6 |

"도구 호출 성공" = 인자 검증을 통과한 호출 / 전체 도구 호출. 형식 오류는 스텝 예산을 쓰지만 루프가 재요청해 회복한다.

† **30B lightning 은 운영 조건에서 사실상 쓸 수 없다 — 14 run 중 11 run 이 LLM 읽기 타임아웃(120s).**
429·503 이 아니라 전부 `TimeoutError('The read operation timed out')` 이고, 1차(4모델 병렬)와 2차(이 모델 1개 프로세스) 모두 같았다.
최소 프롬프트("say ok")는 10초에 200 을 돌려주지만 응답이 `reasoning_content` 로 시작하는 추론형 출력이었다 —
에이전트 프롬프트에선 추론이 길어져 120초를 넘는 것으로 보인다(추정, 토큰 수는 타임아웃이라 못 얻었다).
그래서 이 행은 다른 모델과 같은 기준(NIM 실패 제외)으로 3 run 만 남았고 비교 근거로는 약하다.
타임아웃 난 11 run 에서도 그 전까지의 도구 호출은 15 성공 / 인자 거부 1 / 형식 오류 1 이었다 — 규약 준수 자체보다 **지연**이 문제다.

## 실패의 모양

- **11B — 식별자 혼동 6건, 전부 같은 패턴.** 파드 이름을 `container_lookup` 의 `container_id` 로 넘겼다
  (`{"container_id": "app-0", "node": "node-a"}`). 코드 검증(`12~64자리 16진수`)이 막아 틀린 인자가
  네트워크까지 나간 경우는 0이다. 다만 거부 직후 6건 모두 **다른 도구로 재시도하지 않고 곧바로 `finish`** 했고,
  그중 4건은 결론이 "의심 / 확신 낮음"이었다. 완주는 했지만 조사를 포기한 완주다.
- **550B — 인자 1건, 형식 1건.** `kube_read get events` 를 `name` 없이 호출(목록은 `list` 여야 함) /
  `finish` JSON 안 증거 문자열에서 쉼표 누락 → 재요청 후 완주.
- **120B — 0건.**
- **결론의 모양(참고, 정답 채점 아님):** 같은 스텁 관측에 대해 "의심" 으로 시작하는 분류가
  11B **10/14**, 120B 2/14, 550B 0/14 였다. 작은 모델은 관측을 해석하지 못하면 판단을 "의심" 으로 미룬다.
  운영에선 이게 사람에게 넘어가는 카드 수로 바로 이어진다.

## 읽는 법 · 한계

- **작은 모델도 "완주"는 한다 — 완주율은 변별력이 없다.** 차이는 *틀린 인자를 얼마나 자주 내미느냐*와
  *거부당한 뒤 어떻게 하느냐*에서 난다. 11B 의 13% 거부율은 인자 검증(통제 ①)이 없으면 그대로 잘못된 API 호출이
  된다는 뜻이고, 거부 뒤 곧장 낮은 확신으로 끝내는 패턴은 운영 카드의 "의심" 남발로 이어진다.
- **120B 와 550B 사이에 개선이 없다.** 이 표본에선 운영 기본(120B)이 도구 규약 면에서 550B 와 같거나 낫고,
  LLM 호출 수도 적다. 큰 모델로 올릴 근거는 이 실측에서 나오지 않는다.
- **표본이 작다.** 케이스당 1회(총 14 run/모델), 온도 0.2. 87% 대 98~100% 는 방향만 믿을 만하고
  한두 %p 차이는 잡음 범위다. 반복 수를 늘리려면 `run_model_size.py 3`.
- **소요 시간은 비교하지 않는다.** 벽시계에 NIM 의 429·503 재시도 대기가 섞여 있어 모델 속도가 아니다.
- **분류 품질은 재지 않았다.** 스텁 관측은 한 가지(재시작 3회·BackOff)뿐이라 "옳은 결론"을 채점할 수 없다.
- **NIM 가용성이 운영 변수다.** 1차 병렬 실행에서 120B 6/14, 550B 8/14 가 429·503 재시도 5회 소진으로 실패했다
  (120B 는 재실행 1회, 550B 는 2회 만에 전부 회복). 폴백 없이 단일 모델에 기대면 이 정도 비율로 경보가 조사 없이 끝난다.
  `/v1/models` 목록에 있어도 호출하면 404 인 모델이 여럿이었다. 운영에서 폴백 체인(`NIM_FALLBACK_MODELS`)을 켜 두는 이유다.
