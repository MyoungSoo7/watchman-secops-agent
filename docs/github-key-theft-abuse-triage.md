# 자격증명 탈취·남용 트리아지 — GitHub 마스터키 클래스 (감사로그 연동)

> 대상 시나리오: `fixtures/scenarios/fx-scn-02-github-key-theft-abuse.json`
> 통제 원칙은 그대로다 — **Watchman 은 조사·제안만 하고, 회전·격리·차단을 스스로 실행하지 않는다.**

## 1. 왜 이 클래스를 다루나 (실제 사고 근거)

2026년 6월 **데이원컴퍼니(패스트캠퍼스)** 개인정보 유출은 이 프로젝트가 방어 대상으로 삼는
유형과 정확히 겹친다. 회사 공식 통지에 따르면, **사용 중인 GitHub 서비스의 마스터 계정
키값이 불상의 시점에 탈취**되었고 이를 통해 **5월 9일 최초 침입**이 이루어졌으며, 회사가
사고 가능성을 **인지한 것은 6월 8일** 이다 — 즉 **최초 침입부터 인지까지 약 30일간 탐지되지
않았다.** 유출 항목은 이름·이메일·전화번호·암호화된 비밀번호이고, 주소·직무·직책을 입력한
고객은 그 정보까지 유출됐다. 영향 서비스는 패스트캠퍼스·콜로소·제로베이스·마이라이트·
뉴스프레소·리스픽·샤이니영어·워너스픽 8종이다.[^dayone][^zdnet] 회사는 사후 조치로 **"사고
관련 서비스의 사용자 계정 키 및 주요 권한을 제거"** 했다고 밝혔다 — 자격증명 회전/폐기가
핵심 대응이었음을 보여준다.[^dayone]

이 사고는 단독이 아니라 **2026년 6월 '깃허브 자격증명 탈취' 동시다발 사고군**의 일부다.
같은 시기 티빙은 침해 신고서에서 **AWS 키를 폐기하고 자격증명을 교체**했고, 보안 업계는
정보 유출 자체보다 **탈취한 키로 DB·인프라에 직접 접근하는 단계**를 더 심각하게 봤다.[^news1]

핵심은 **"키가 뚫린 것"보다 "뚫린 뒤 30일간 아무도 abuse 를 못 본 것"** 이다. 초기 자격증명
유출을 막지 못하는 상황을 전제로, **탈취된 자격증명이 '사용되는' 순간의 이상 신호를 조기에
잡아 사람에게 근거와 함께 올리는 것** 이 Watchman 이 이 클래스에 기여하는 지점이다.

## 2. 정직한 경계 — Watchman 이 하는 것과 못 하는 것

이 클래스는 두 층으로 갈린다. 섞으면 과장이 된다.

**[예방層 — Watchman 밖, 상류(개발자 플랫폼) 통제]**
키가 유출되는 것 자체는 Watchman 이 못 막는다. 이건 다음이 담당한다:
- **GitHub Push Protection + secret scanning** — 시크릿을 push 단계에서 차단.
- **장수(長壽) 마스터키 폐지 → OIDC 워크로드 아이덴티티(단명 토큰) + 최소권한(PoLP)**.
- **시크릿을 코드 밖 KMS/Secret Manager 로** 이관.

실제로 사고 이후 **KISA·방송통신위원회는 "개발자 플랫폼에 자격증명 저장 금지"를 권고**했다.[^news1]
이게 root fix 이며, Watchman 이 이걸 한다고 표기하면 거짓이다.

**[탐지·대응層 — Watchman 의 자리]**
훔친 자격증명이 **사용되는 순간** 관측 가능한 이상 신호로 드러난다. 그 신호가 Alertmanager 로
오면 Watchman 이 트리아지하고 봉쇄를 **제안**한다. 데이원 사고의 30일 잠복 = 바로 이 층의 부재
("비정상 데이터 접근 경보 미설정 + 상시 모니터링 부재")였다.

## 3. 탐지 신호 (감사 평면 → Alertmanager → Watchman)

탈취된 자격증명의 남용은 **감사(audit) 로그** 에 흔적을 남긴다. 단계별로:

| 킬체인 단계 | 관측 신호 | 소스(수집 전제) | Watchman 도달 |
|---|---|---|---|
| GitHub 남용 | 낯선 IP/ASN 의 토큰 사용, PAT 신규 발급, 조직 권한 변경 | GitHub Audit Log API | ES 수집 시 |
| 클라우드 피벗 | SA 키 이상 위치 사용, storage 대량 get, IAM 변경 | GCP Cloud Audit Logs | ES 수집 시 |
| **클러스터 측면이동** | **배포 신원이 다수 ns 에서 secret 대량 list/get, exec, 신규 배포** | **kube-apiserver audit** | **Watchman 이 kube_read 로 직접 교차확인 가능** |
| 데이터 접근·유출 | 이상 대량 SELECT·비인가 쿼리, 이그레스 급증 | DB 감사 · NetworkPolicy deny · Falco | ES 수집 시 |

픽스처 `fx-scn-02-github-key-theft-abuse.json` 은 이 중 **가장 데모 가능한 클러스터 측면이동
신호**를 재현한다: GitHub Actions OIDC 로 연동된 배포용 ServiceAccount
(`system:serviceaccount:ci-cd:github-actions-deployer`)가 평소 대상이 아닌 다수 네임스페이스에서
`secrets` 를 list/get 하고, 고객 DB 접속정보 secret 까지 조회하며, 새벽·미등록 ASN·정상 CI
파이프라인 부재라는 정황을 동반한다(라벨 `source=kube-apiserver-audit`, `severity=critical`).

**경로: 감사로그 → (SIEM 룰) → Alertmanager → Watchman webhook.** Watchman 입장에서는 그냥
또 하나의 Alertmanager 알림이므로 **새 수집 도구가 필요 없다.** 단, **이 알림이 존재하려면
감사로그가 먼저 ES/SIEM 으로 수집·룰화되어 있어야 한다** — 이 전제가 이 클래스의 핵심 통합
작업이며 아래 §6 에 STRETCH 로 정직히 남긴다.

## 4. Watchman 의 트리아지 (관측→판단→제안, 실행 없음)

1. **관측(read-only)** — 기존 두 도구만 쓴다.
   - `es_search`: 해당 신원(SA/토큰)의 활동 타임라인, 접근한 secret·리소스, 이그레스 흔적 상관.
   - `kube_read`(GET/LIST): 그 ServiceAccount 의 RoleBinding·권한 범위, 대상 네임스페이스·
     워크로드·이벤트를 직접 조회해 "원래 이 신원이 건드릴 자원인가"를 교차확인.
2. **판단** — **"정상 CI 작업 아닌가"** 라는 대체가설을 강제 검토(직전 파이프라인 실행 상관·
   소스 IP·시각·평소 배포 대상과 대조), novel 한 자격증명 남용 여부와 확신도를 분류.
3. **제안(실행 아님)** — 카드에 담는 **봉쇄 제안**은 사람이 승인·집행한다:
   - 해당 **자격증명만 회전·폐기**, 조직 토큰 일괄 재발급 + OTP 강제 — *제안*.
   - 문제 **ServiceAccount 비활성 / 워크로드 이그레스 차단**(NetworkPolicy deny) — *제안*.
   - **포렌식 보존**(감사로그·접근 이력 스냅샷) 후 영향 범위 산정 — *제안*.
   - 예방層 후속(**OIDC 단명 토큰 전환·시크릿 스캐닝·PoLP**) 착수 — *제안*.

이 시나리오에서도 6축 통제는 그대로 유효하다: 제안 카드는 **텍스트일 뿐**이고(④ 실행 도구
없음), 알림 본문에 섞인 지시는 주입 감지층이 잡으며(①), 에이전트는 여전히 읽기 전용·비루트·
이그레스 허용목록 안에서만 돈다(②③⑥). 즉 **"방어 대상(자격증명 탈취·남용)"을 다루면서도
에이전트 자신이 새로운 공격면이 되지 않는다.**

## 5. 실측 (P4 정직 원칙 — 측정한 것만)

`fixtures/scenarios/fx-scn-02-github-key-theft-abuse.json` 을 **결정론적 mock 파이프라인**으로
1회 통과시킨 결과(`LLM_MODE=mock`, 감사로그 격리):

- 루프: **완주(state=완료, partial=None)**, finish 스키마 **유효**, evidence **1건**.
- 주입 감지(봉투 전체 JSON 스캔): **0건** — 단, **이 값은 처음엔 2건이었다(아래).**

> mock 은 **분류 정확도가 아니다.** 제어 흐름·출력 계약·주입 오탐 없음만 재현 검증한다(다른
> 뱅크와 동일 기준). 실 NIM 분류 정확도는 in-cluster 실관측 run 채점이 근거다.

### 5.1 이 시나리오가 드러낸 실제 결함 — 주입 감지 오탐 (발견·수정 완료)

이 픽스처를 처음 돌렸을 때 주입 감지가 **2건 오탐**(`exfil`·`exfil-reverse`)했다. 원인을 실측하니
정규식의 영문 동사 `post` 가 **단어경계 없이** 매칭돼 **`post`gres-app-credentials** 의 "post"를
공격 동사로 오인한 것이었다(자격증명을 언급하는 정상 보안 경보에서 매우 흔한 문자열).
즉 프로덕션 주입 감지층의 substring 오탐이며, 제출서의 "오탐 0" 주장에 대한 반례였다.

**수정:** 영문 동사에만 `\b` 단어경계 적용(한글 동사는 CJK 라 제외). 회귀 게이트 전수 재검증:
- 레드팀 코드 감지층: **감지 12/12 · 오탐 0/12** (진짜 exfil 인 fx-rt-05·06 그대로 탐지) ✅
- 케이스 파이프라인(mock): **10/10** (전 케이스 주입 0) ✅
- fx-scn-02: 주입 **2 → 0**, 판정 **PASS** ✅

동결 수치(12/12·10/10)를 깨지 않고 오탐만 제거했다. **시나리오 설계가 실제 코드 결함을
드러내고 회귀 게이트로 안전하게 고친** 사례로, 이 프로젝트의 P4·레드팀 게이트가 작동함을
보인다.

## 6. 범위와 남은 일 (정직)

- **된 것**: 알림 픽스처 + 킬체인 신호 매핑 + 트리아지/제안 설계 + mock 파이프라인 완주 실측
  + (부수) 주입 감지 오탐 발견·수정·회귀검증.
- **아직 안 된 것(STRETCH)**: 이 클래스의 알림이 실제로 존재하려면 **GitHub Audit Log·GCP
  Cloud Audit·kube-apiserver audit·DB 감사로그를 ES/SIEM 으로 수집하고 이상 룰(대량 secret
  열람·비인가 쿼리·이상 위치 자격증명 사용)을 세워 Alertmanager 로 라우팅**하는 파이프라인이
  필요하다. 이건 프로토타입 제출 범위 밖이며 ROADMAP STRETCH 로 둔다 — **설계·픽스처·트리아지
  로직은 갖췄고, 감사로그 수집 배선은 미완**임을 그대로 표기한다.
- **예방層(Push Protection·OIDC·KMS·PoLP)은 Watchman 밖**이다. 이 문서는 그 경계를 명시한다.
