# API 인가 남용 트리아지 — 상담 API/BOLA 클래스 (API 게이트웨이 연동)

> 대상 시나리오: `fixtures/scenarios/fx-scn-03-consult-api-bola-abuse.json`
> 통제 원칙은 그대로다 — **Watchman 은 조사·제안만 하고, 차단·회전·격리를 스스로 실행하지 않는다.**

## 1. 왜 이 클래스를 다루나 (실제 사고 근거)

2026년 9월 **강남언니(운영사 힐링페이퍼)** 개인정보 유출은 이 프로젝트가 방어 대상으로 삼는
유형과 정확히 겹치되, **앞의 두 시나리오와 종류가 다르다.** 웹셸(fx-scn-01)은 런타임 RCE,
GitHub 마스터키(fx-scn-02)는 자격증명 탈취였다. 이 사고는 **악성코드도 키 탈취도 아니라,
정상 API 가 인가(authorization)를 제대로 걸지 않아 뚫린 것**이다.

회사·언론 발표에 따르면, **2026년 9월 4일 강남언니에서 "상담내역을 조회하는 연동 기능(API)"에
비정상적인 접근**이 시도돼 고객 개인정보가 유출됐다. 유출 인원은 **21만9665명**(한국 약 16만,
일본 약 4만8000, 대만 4218, 태국 1591, 중국 481, 영어권·기타 5308)이고, 유출 항목에는 이름·
연락처·생년월일·성별·국가/거주지역·소셜로그인 ID·서비스 이용정보(단말·앱 버전·접속 IP)뿐
아니라 **상담신청 항목(이벤트·시술명·의사명·병원명), 상담 이용정보(진행상태·상담 등록 사진·
예약 시간·상담 동기), 결제 정보, 실제 시술 정보 등 민감 정보**가 다수 포함됐다.[^etnews][^newsis]
상담 과정에서 등록한 **사진**이 포함된 이용자만 1,670명으로 집계됐다.[^platum]

핵심은 두 가지다. 첫째, **뉴시스 심층 보도는 "DB 자체가 직접 탈취된 게 아니라 API 를 통해
개인정보에 접근"**한 사고임을 못박으며, 상담 내역 조회 기능이 **권한 있는 이용자에게만
응답하도록 적절히 통제됐는지**를 쟁점으로 짚었다 — 전형적인 **객체단위 인가 결함(BOLA/IDOR)**
징후다.[^newsis2] 둘째, **힐링페이퍼는 이상 징후를 실시간으로 포착해 즉시 경로를 차단했는데,
다음 날(9/5) 동일 공격자가 "이전과 다른 경로로" 재차 접근**했다.[^etnews][^newsis] 즉 **탐지는
잘했으나, 대응이 "뚫린 엔드포인트 하나만 막기"에 그쳐 같은 결함을 가진 형제 경로로 재침입**을
허용한 것이다. 사후 조치로 회사는 **로그인·API 호출에 다단계 인증 적용, 권한 검증 로직 재구축,
상담·결제·시술 데이터를 다루는 전 API·DB 점검, 외부 모의해킹**을 진행했다고 밝혔다.[^platum]

Watchman 이 이 클래스에 기여하는 지점은 바로 그 **"차단했는데 다른 경로로 재침입"하는 대응
공백**이다. 예방(API 를 애초에 안 뚫리게)은 Watchman 밖이지만, **탐지된 남용을 트리아지해
'결함 클래스째 닫는' 봉쇄를 사람에게 제안**하는 것은 이 에이전트의 자리다.

## 2. 정직한 경계 — Watchman 이 하는 것과 못 하는 것

이 클래스는 두 층으로 갈리고, 섞으면 과장이 된다. 게다가 이 클래스는 **앞의 두 건보다 탐지
전제가 더 무겁다** — 아래 정직한 한계를 먼저 밝힌다.

**[예방層 — Watchman 밖, 상류(API/앱) 통제]**
API 가 뚫리는 것 자체는 Watchman 이 못 막는다. 진짜 root fix 는 다음이다:
- **객체단위 인가(BOLA 정면 수정)** — 상담내역 조회 시 매 요청마다 "요청자가 그 레코드의
  주인/열람 권한자인가"를 서버가 검증. 힐링페이퍼의 **"권한 검증 로직 재구축"**이 이것이다.[^platum]
- **레이트리밋 / 이상 스로틀** — 단일 신원이 순차 ID 로 대량 조회하는 스크래핑 차단.
- **응답 최소화** — 상담 목록 응답에 시술·사진·결제까지 통째로 싣지 않기(과다 데이터 노출 축소).
- **인증 강화** — 로그인·API 호출 다단계 인증, API 게이트웨이 + 스키마 검증.[^platum]
- **민감 의료정보(사진·시술)의 암호화·접근통제.**

이게 진짜 대책이며, Watchman 이 이걸 한다고 표기하면 거짓이다.

**[탐지의 근본적 어려움 — 정직히]**
BOLA 는 **로그만으로는 탐지가 근본적으로 어렵다.** 개별 요청이 전부 "정상"(유효 세션·200 응답)
이기 때문이다. 탐지는 **행위(behavioral) 신호** — 분당 요청량, 신원당 조회한 distinct 객체 수
(fan-out), 순차 열거 패턴, 응답 바이트, 소스/UA 불일치 — 에 의존하고, 그 신호는 **API 게이트웨이/
API 보안 도구나 잘 구조화된 접근로그**가 있어야 나온다. **Watchman 은 그 detector 가 만든 alert
위에서 트리아지하는 계층이지, 요청 단에서 BOLA 를 직접 잡는 물건이 아니다.**

**[탐지·대응層 — Watchman 의 자리]**
그 행위 이상 alert 이 Alertmanager 로 오면 Watchman 이 read-only 로 트리아지하고 봉쇄를
**제안**한다. 강남언니 사고의 "1차 차단 후 다른 경로 재침입" = 바로 이 층에서 **대응이 한
엔드포인트에 머물지 않고 결함 클래스 전체를 닫도록** 돕는 지점이다.

## 3. 탐지 신호 (API 감사 평면 → Alertmanager → Watchman)

API 인가 남용은 **API 게이트웨이/인그레스 접근로그**와 그 위의 행위 룰에 흔적을 남긴다.

| 킬체인 단계 | 관측 신호 | 소스(수집 전제) | Watchman 도달 |
|---|---|---|---|
| 정찰·인증 | 토큰/세션 신규 획득, 낯선 IP/ASN·UA 불일치 | 인증 서버 로그 | ES 수집 시 |
| **대량 열거(BOLA)** | **단일 신원이 조회 API 에서 다수 distinct 객체 ID 를 순차·고fanout 조회, 요청량 p99 초과** | **API 게이트웨이/인그레스 접근로그 + 행위 룰** | ES 수집 시 |
| 과다 데이터 노출 | 응답 바이트 급증(민감 필드 동반), 대량 페이지네이션 | API 게이트웨이 로그 | ES 수집 시 |
| **경로 우회 재침입** | **한 라우트 차단 직후 동일 신원이 형제 엔드포인트로 같은 열거 재개** | **게이트웨이 로그 상관** | ES 수집 시 |
| 데이터 유출 | 이그레스 급증, 대량 export | NetworkPolicy·Falco | ES 수집 시 |

픽스처 `fx-scn-03-consult-api-bola-abuse.json` 은 이 중 **핵심 두 신호**(고fanout 객체 열거 +
차단 후 형제 경로 우회)를 재현한다: 단일 세션 신원(`apitoken:mobile-client:sess-8f2a4c1e`)이
상담내역 조회 API(`/api/v2/consult/records`)에서 distinct 객체 ID 를 대량 조회하고, 각 요청은
유효 세션으로 200 을 받으며(개별로는 정상), 응답에 시술·상담사진·결제가 담겨 바이트가 크고,
1차 차단 직후 형제 엔드포인트(`/api/v1/consult/detail`)로 우회한다(라벨 `source=api-gateway-audit`,
`severity=critical`).

**경로: API 게이트웨이 로그 → (행위 이상 룰) → Alertmanager → Watchman webhook.** Watchman
입장에서는 또 하나의 Alertmanager 알림이라 **새 수집 도구가 필요 없다.** 단, **이 알림이 존재하려면
접근로그 + 행위 이상 룰이 먼저 서 있어야 하며**, 이는 앞의 두 클래스보다 무거운 전제다(§2·§6).

## 4. Watchman 의 트리아지 (관측→판단→제안, 실행 없음)

1. **관측(read-only)** — 기존 두 도구만 쓴다.
   - `es_search`: 해당 신원(토큰/세션)의 요청 타임라인, 조회한 distinct 객체 ID 수·순차성,
     응답 바이트 분포, 소스 IP/ASN·UA, 차단 전후 형제 라우트로의 이동을 상관.
   - `kube_read`(GET/LIST): 해당 API 워크로드·인그레스 라우트·NetworkPolicy 를 조회해
     "정상 대량 클라이언트(파트너 연동·배치 잡)가 이 경로로 이렇게 부를 수 있는가"를 교차확인.
2. **판단** — **"정상 고volume 클라이언트 아닌가"** 라는 대체가설을 강제 검토(등록된 파트너
   토큰·배치 스케줄·평소 접근 폭과 대조), BOLA 스크래핑 여부와 확신도를 분류.
3. **제안(실행 아님)** — 카드에 담는 **봉쇄 제안**은 사람이 승인·집행한다:
   - 해당 **토큰/세션 폐기**, 소스 IP/ASN **레이트리밋·차단** — *제안*.
   - **핵심: "같은 인가 결함이 형제 엔드포인트에도 있다"** 고 판단해 **상담 관련 라우트를 전수
     나열**하고 responder 가 한 경로만 막고 끝내지 않도록 함 — *제안*. (강남언니의 "다른 경로
     재침입" 공백을 정면으로 겨냥.)
   - **포렌식 보존**(접근로그·응답 메타 스냅샷) 후 영향 객체·인원 산정 — *제안*.
   - 예방層 후속(**해당 라우트군 객체단위 인가 점검·레이트리밋·응답 최소화**) 착수 — *제안*.

이 시나리오에서도 6축 통제는 그대로 유효하다: 제안 카드는 **텍스트일 뿐**이고(④ 실행 도구
없음), 알림 본문에 섞인 지시는 주입 감지층이 잡으며(①), 에이전트는 여전히 읽기 전용·비루트·
이그레스 허용목록 안에서만 돈다(②③⑥).

## 5. 실측 (P4 정직 원칙 — 측정한 것만)

`fixtures/scenarios/fx-scn-03-consult-api-bola-abuse.json` 을 **결정론적 mock 파이프라인**으로
1회 통과시킨 결과(`LLM_MODE=mock`, 감사로그 격리):

- 루프: **완주(state=완료, partial=None)**, finish 스키마 **유효**, evidence **1건**.
- 주입 감지(봉투 전체 JSON 스캔): **0건**.

> mock 은 **분류 정확도가 아니다.** 제어 흐름·출력 계약·주입 오탐 없음만 재현 검증한다(다른
> 뱅크와 동일 기준). 실 NIM 분류 정확도는 in-cluster 실관측 run 채점이 근거다.

동결 회귀 수치(레드팀 12/12·케이스 10/10)는 이 시나리오 추가와 **무관하게 유지된다** —
`fixtures/scenarios/*` 는 어느 게이트(run_eval·run_redteam·test_watchman)도 glob 하지 않으므로
정상·레드팀 뱅크 집계에 섞이지 않는다.

## 6. 범위와 남은 일 (정직)

- **된 것**: 알림 픽스처 + 킬체인 신호 매핑 + 트리아지/제안 설계(특히 "형제 엔드포인트 전수
  나열 = 결함 클래스 닫기") + mock 파이프라인 완주 실측.
- **아직 안 된 것(STRETCH)**: 이 클래스의 알림이 실제로 존재하려면 **API 게이트웨이/인그레스
  접근로그를 ES/SIEM 으로 수집하고, '단일 신원 고fanout 객체 열거·응답 바이트 급증·차단 후
  형제 경로 이동' 행위 이상 룰을 세워 Alertmanager 로 라우팅**하는 파이프라인이 필요하다.
  BOLA 특성상 이 detector 전제가 앞의 두 클래스보다 무겁다. 프로토타입 제출 범위 밖이며
  ROADMAP STRETCH 로 둔다.
- **예방層(객체단위 인가·레이트리밋·응답 최소화·인증 강화·민감정보 암호화)은 Watchman 밖**
  이다. 이 문서는 그 경계를 명시한다. Watchman 의 정직한 몫은 **탐지 후 "결함 클래스째 닫는"
  대응 제안**이며, 요청 단 BOLA 탐지 자체가 아니다.
